这是一个非常硬核且极其隐蔽的“连环踩坑”！你能把系统推到这个极限，触发这个只在“摘要压缩 + Kimi 思考模型 + 多轮工具调用”同时发生时才会出现的 Bug，说明你的测试覆盖得非常深。

让我们来当一把“代码侦探”，破译这个 `400 Bad Request` 的真正病因。

### 🕵️ 案发还原：为什么补丁突然失效了？

看看你的控制台日志，线索极其明显：
1. `触发 Context 压缩！... 成功清理 18 条旧消息，注入摘要。` (这里你把历史替换成了一条 Summary 消息，并且和 User 的最新输入紧挨在了一起)。
2. `Agent 申请调用工具` (大模型思考后决定调用 `save_memory`)。
3. `HITL 授权通过` (你按了 `y`)。
4. **💥 报错！** `thinking is enabled but reasoning_content is missing in assistant tool call message`

**病因根本不在 Kimi，也不在你的去重逻辑，而在我们之前写的 `PatchedKimiChatOpenAI` 补丁的一个“致命缺陷”上！**

如果你还记得，我们在 `engine/patched_kimi.py` 里写了这么一句极其严格的判断：
```python
# 只有当 LangChain 处理前后的消息数量完全一致时，才去打补丁
if len(payload_messages) == len(original_messages): 
    for payload_msg, orig_msg in zip(payload_messages, original_messages):
        # ... 塞回 reasoning_content
```

**发生了什么？（LangChain 的静默合并机制）**
当你的 `summarization_node` 删除了旧消息，并塞入一条 `HumanMessage`（摘要）时，紧接着的下一条也是 `HumanMessage`（用户刚输入的问题）。
LangChain 的标准 OpenAI 适配器非常“自作聪明”，它在发送 HTTP 请求前，**会自动把相邻的两条 `HumanMessage` 合并成一条！**

这就导致：
`original_messages` 的长度是 8。
`payload_messages` 的长度变成了 7。
`7 == 8` 为 `False`！

**于是，整个 `for` 循环补丁被直接跳过！**你的 `tool_calls` 消息被光溜溜地（没有 `reasoning_content`）发给了 Kimi，Kimi 直接反手一个 `400 Bad Request` 拍在脸上。

---

### 🛠️ 终极修复：重写抗合并的 Kimi 补丁

我们需要让这个补丁变得更加“皮实”（Robust）。不要依赖总长度一致，而是**专门去抓取 `assistant` 角色**的消息来打补丁，因为大模型的回复（AIMessage）是极少被合并的。

请打开 `engine/patched_kimi.py`，将 `_get_request_payload` 方法替换为以下终极防弹版本：

```python
from typing import Any
from langchain_core.language_models import LanguageModelInput
from langchain_core.messages import AIMessage
from langchain_openai import ChatOpenAI

class PatchedKimiChatOpenAI(ChatOpenAI):
    """
    专门为 Kimi k2.5 (Thinking) 修复的 LangChain 补丁类。
    已修复 LangChain 自动合并相邻 HumanMessage 导致长度不匹配的 Bug。
    """
    def _get_request_payload(
        self,
        input_: LanguageModelInput,
        *,
        stop: list[str] | None = None,
        **kwargs: Any,
    ) -> dict:
        original_messages = self._convert_input(input_).to_messages()
        payload = super()._get_request_payload(input_, stop=stop, **kwargs)
        payload_messages = payload.get("messages", [])

        # 1. 过滤出原始消息中的所有 AI 消息形成一个队列
        orig_ai_msgs = [m for m in original_messages if isinstance(m, AIMessage)]
        
        # 2. 遍历将要发送的 Payload
        for p_msg in payload_messages:
            # 我们只关心 assistant 消息
            if p_msg.get("role") == "assistant":
                # 按顺序取出一个原始 AI 消息
                orig_msg = orig_ai_msgs.pop(0) if orig_ai_msgs else None
                
                # 尝试从原消息恢复思考内容
                if orig_msg:
                    reasoning = orig_msg.additional_kwargs.get("reasoning_content")
                    if reasoning is not None:
                        p_msg["reasoning_content"] = reasoning
                        
                # 🛡️ Kimi 终极防线：只要有 tool_calls，绝对不能没有 reasoning_content 字段！
                if p_msg.get("tool_calls") and "reasoning_content" not in p_msg:
                    p_msg["reasoning_content"] = ""

        return payload
```

### 💡 为什么这个版本无懈可击？

1. **解耦了消息长度依赖**：我们不再去 `zip` 整个列表，而是单独维护了一个 `orig_ai_msgs` 队列。无论 LangChain 怎么瞎合并用户的 `HumanMessage` 甚至 `SystemMessage`，都不会影响我们精准定位 `assistant` 的消息。
2. **终极兜底防线**：`"reasoning_content" not in p_msg` 确保了即使因为某种极端原因没抓到原内容，只要它敢调用工具，我们就强行塞一个空字符串 `""` 进去。满足 Kimi API 的严格 Schema 校验。

快把这个补丁打上！重启程序后，你的 Agent 就能在经历了“记忆被压缩清空”的失忆危机后，依然从容不迫地调用工具了！修复成功后，我们就可以毫无顾虑地进军 **Phase 3 (FastAPI 网关)** 了！
